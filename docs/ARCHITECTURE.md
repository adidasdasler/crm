# Архитектура и ключевые решения

Этот документ фиксирует, **что изменено по сравнению со спецификацией v3.0** и почему.

## Изоляция салонов (multi-tenancy)

- Каждая таблица салона имеет поле `tenantId` и политику RLS с `FORCE` (миграция `0002_rls_constraints`).
- Приложение подключается ролью **`salon_app`**: она не владелец таблиц, не суперпользователь и без `BYPASSRLS`. Без этого RLS молча не работает, и в v3.0 это не было учтено.
- Каждый запрос выполняется в `prisma.withTenant(tenantId, tx => …)`, то есть в транзакции с `set_config('app.tenant_id', …, true)`. Если `tenant_id` не задан, БД не возвращает ни одной строки.
- Системное подключение (владелец схемы) используется только там, где тенант ещё неизвестен: вход, обновление токена, приглашение сотрудника. В будущем к ним добавятся webhooks и фоновые задачи.
- Роли `salon_app` недоступны колонки `User.passwordHash` и таблица `RefreshToken`.

## Пользователи

- В v3.0 email был уникален внутри салона (`[tenantId, email]`). Теперь **один глобальный `User`** и `Membership(userId, tenantId, role)`. Иначе при входе непонятно, в какой салон входит человек, а мастер не может работать в двух салонах.

## Записи

- **Двойная запись** запрещена ограничением БД `EXCLUDE USING gist (tenantId =, resourceId =, tstzrange(startsAt, blockedUntil) &&)` для активных статусов. Advisory lock из v3.0 не защищал от пересечения записей с разным временем начала.
- `endsAt` — конец визита для клиента. `blockedUntil` — конец с учётом технического перерыва.
- **`BookingItem`**: в одном визите может быть несколько услуг, а цена и длительность сохраняются на момент записи.
- **`TimeOff`**: отпуск, больничный, перерыв.
- Онлайн-запись принимает только время, которое `slots()` вернул как свободное. Сотрудник может поставить запись вне графика, указав `allowOutsideSchedule`.
- Клиент управляет записью по ссылке с токеном. В БД хранится только SHA-256 токена.

## Авторизация

- Веб: httpOnly cookie (`SameSite=Lax`) и обязательный заголовок `X-Requested-With` для изменяющих запросов (CSRF). В v3.0 было `SameSite=strict`, а с ним после возврата из ЮKassa пользователь оказался бы разлогинен.
- Мобильное приложение: `Authorization: Bearer`, refresh-токен хранится в SecureStore (Keychain/Keystore).
- JWT HS256: один сервис, один секрет. RS256 имеет смысл, когда токены проверяют несколько сервисов.
- 2FA (TOTP) не обязательна. Её добавим как опцию на этапе 2: обязательная 2FA для владельца салона, работающего с телефона, убьёт конверсию.

## Деньги и время

- Деньги хранятся в `Int` в копейках. В v3.0 было противоречие: «Decimal в копейках».
- Время хранится как `timestamptz` в UTC. Сетка слотов считается в часовом поясе салона (luxon).

## Фронтенд

- **Обычный роутинг (BrowserRouter), а не HashRouter.** Страницы записи салонов должны индексироваться поисковиками: это бесплатный трафик.
- Страница записи салона: `mioflow.ru/b/<slug>`. Wildcard-поддомены и сертификаты для них не нужны.
- CRM — Expo-приложение, которое одновременно служит веб-версией (`app.mioflow.ru`). Три отдельных SPA из v3.0 заменены на два приложения.
- Обновления в реальном времени: на старте календарь опрашивает сервер раз в 30 секунд. Socket.io добавим, когда появится инбокс.
- API работает на том же домене (`/v1`), поэтому CORS и общий cookie-домен не нужны.

## Напоминания и фоновые задачи

- Очередь — сама таблица `Reminder` в PostgreSQL. Воркер (`src/worker.ts`, отдельный контейнер) раз в 30 секунд «арендует» созревшие строки через `FOR UPDATE SKIP LOCKED`. Redis и BullMQ из v3.0 не нужны: меньше компонентов, задачи не теряются при перезапуске, можно запускать несколько воркеров.
- Канал выбирается в момент отправки. Порядок: Telegram → MAX → ВКонтакте → email (`src/notify/channels.ts`, общий интерфейс «текст + кнопки»). Все каналы бесплатны; SMS отказались, чтобы не перекладывать расходы на салоны. Если бот заблокирован, привязка снимается и берётся следующий канал. Повторы при ошибке — через 1, 5 и 15 минут.
- Ссылка «управлять записью» есть у каждой записи: токен = HMAC(id записи), в БД хранится только его хэш. Поэтому ссылку можно вставить в любое сообщение в любой момент.

## Подписка

- Оплата по ссылке (ЮKassa или тестовый mock-провайдер в разработке), без автосписаний. Новый срок прибавляется к концу текущего оплаченного или пробного периода.
- Вебхук ЮKassa проверяется по IP, а статус платежа перезапрашивается через API ЮKassa. Обработка идемпотентна.
- Статусы: `TRIAL`/`ACTIVE` → (срок истёк) `PAST_DUE` (3 льготных дня, всё работает) → `EXPIRED`: изменяющие запросы получают `402 SUBSCRIPTION_EXPIRED`, онлайн-запись выключена, данные сохраняются.

## Роли и права

- Роль (OWNER, MANAGER, ADMIN, MASTER) задаёт набор прав по умолчанию (`src/common/permissions.ts`). Владелец включает и выключает права для остальных ролей в «Ролях и доступах»; настройки хранятся в `Tenant.settings.permissions` и меняются только отдельным эндпоинтом `PUT /tenant/permissions` (только OWNER).
- Проверка — в глобальном `AuthGuard`: декоратор `@Can('perm')` на эндпоинте, права салона кэшируются на 10 секунд. Владелец может всё; оплата подписки — только владелец; назначить или изменить управляющего — только владелец.
- Без `bookings.all` сотрудник видит только записи своего мастера, без `customers.view` — только своих клиентов, без `customers.contacts` телефоны и email маскируются на сервере.

## Мини-сайт и карты

- Страница `mioflow.ru/b/<slug>` — мини-сайт и запись в одном: описание, часы работы (из графиков мастеров), адрес, ссылки, услуги.
- Поисковым роботам и превью ссылок Nginx по User-Agent отдаёт готовый HTML с разметкой schema.org (`GET /v1/public/<slug>/page`), людям — SPA. Содержимое одинаковое, это не клоакинг.
- Метка `?src=yandex|2gis|vk|qr…` сохраняется в `Booking.referrer`; «Обзор» показывает, сколько клиентов пришло с каждой площадки. QR-коды — `GET /v1/public/<slug>/qr.svg|png`.

## Отрасли

- `src/common/industries.ts`: сфера меняет слова интерфейса («мастер» / «тренер» / «преподаватель»), стартовые услуги при регистрации и тип в разметке schema.org. Ядро (ресурсы, услуги, записи, напоминания) общее.
- Медицина не поддерживается: лицензия и специальная категория ПДн (ст. 10 152-ФЗ).
- Следующие шаги масштабирования: групповые занятия (несколько клиентов на слот), ресурсы-помещения (кабинет, бокс, зал) и сети филиалов — модель `Resource` это допускает.

## Склад

- Таблицы `Material`, `MaterialBatch` (партия: цена и срок годности), `StockMovement` (журнал, только добавление), `ServiceMaterial` (норма расхода на услугу). Все под RLS, как остальные данные салона.
- Количества — целые тысячные доли единицы (1 мл = 1000), без дробных чисел в БД.
- Расход идёт с партий, срок которых истекает раньше (FEFO). Остаток может уйти в минус, если визит завершили раньше, чем оприходовали материал; следующий приход сначала покрывает недостачу. Инвариант: сумма остатков партий = max(остаток, 0).
- Автосписание — в той же транзакции, что и перевод записи в `COMPLETED` (`src/stock/stock.ts`). Откат завершения возвращает материал в те же партии; повторное завершение не списывает дважды. Комплекс без своих норм использует нормы входящих услуг.
- Отраслевые наборы материалов с нормами — `src/stock/templates.ts`, привязываются к услугам по названию.

## Оценки и советы

- `Review` — одна оценка на запись (1–5, комментарий, канал). Просьба оценить — напоминание типа `AFTER_VISIT` через 2 часа после окончания визита; снимается, если завершение отменили или оценка уже есть. Кнопки `r:<оценка>:<id>` проверяют, что нажимает клиент этой записи. Следующее сообщение клиента в течение суток сохраняется как комментарий.
- Оценка 1–3 — сразу уведомление владельцу (Telegram и push) с телефоном клиента, чтобы уладить ситуацию до отзыва на картах. 4–5 — кнопки «Отзыв на Яндекс Картах / в 2ГИС», если салон указал ссылки на карточки.
- Советы (`src/insights/insights.ts`) — правила без ИИ, каждую цифру можно проверить. Все запросы явно фильтруются по `tenantId`, поэтому функция работает и под RLS (`GET /analytics/insights`), и в воркере. Сводка — в понедельник с 10:00 по времени салона; `Tenant.insightsSentAt` отмечается до отправки, чтобы не прислать дважды.

## Депозиты и абонементы

- MioFlow только ведёт учёт. Деньги принимает салон (наличные, карта, перевод) и выдаёт чек сам: на аванс за услуги чек обязателен (54-ФЗ). Принимать деньги клиентов салонов на счёт владельца сервиса нельзя — для самозанятого это агентская деятельность, запрещённая на НПД.
- Баланс клиента — `Customer.balance` (деньги, возвратные) и `Customer.bonus` (бонусы, невозвратные), журнал — `AccountEntry` (только добавление, защищено правами БД). Визит оплачивается с баланса пропорционально; при возврате денег сгорает пропорциональная часть бонусов. Клиент вправе потребовать вернуть неизрасходованный аванс (ст. 32 Закона о защите прав потребителей), поэтому бонус оформлен как подарок салона, а не как деньги.
- Абонемент: вид (`PassPlan`) и проданный клиенту (`CustomerPass`, условия копируются в момент продажи). Покрывает визит, если все услуги входят в абонемент (комплекс — если входят все его части) и время визита попадает в окно (дни недели, часы). Безлимит — не больше одного визита в день.
- Расчёт за визит — в той же транзакции, что и перевод записи в `COMPLETED` (`src/loyalty/loyalty.ts`): сначала абонемент с ближайшим сроком окончания, иначе — депозит (если включено автосписание). Откат завершения возвращает визит в абонемент и деньги на баланс; повторное завершение не списывает дважды.

## Офлайн-режим

- Кэш React Query сохраняется в хранилище устройства (AsyncStorage, в вебе — localStorage) до 7 дней: только расписание, записи, услуги, мастера, клиенты, отчёты (`PERSIST_KEYS` в `src/lib/offline.ts`). Запросы работают в режиме `offlineFirst`: без сети показываются сохранённые данные, а не ошибка. Календарь заранее загружает 3 следующих дня.
- Профиль пользователя сохраняется, поэтому открыть приложение без сети можно, если вход уже был. Сбой сети при обновлении токена — не выход из аккаунта.
- Отметки статуса без сети ставятся в очередь (`mioflow-outbox-v1`) и сразу видны на экране. Отправка — при появлении связи, при следующем запуске и раз в 30 секунд, пока очередь не пуста. Отправляется версия записи, которую видел сотрудник: если запись изменили (`BOOKING_VERSION_MISMATCH`) или переход уже невозможен, отметка не применяется и показывается как конфликт.
- Создание записей без сети запрещено: гарантию «двойная запись невозможна» даёт ограничение в базе, а без сервера его не проверить.
- Определение сети: в браузере — события `online`/`offline`, на телефоне — NetInfo с проверкой доступности через собственный `/v1/health` (не через серверы Google).

# Безопасность и защита персональных данных MioFlow

> Это технический отчёт разработчика, а не юридическое заключение. Окончательные решения о соответствии 152-ФЗ — модель угроз, уровень защищённости, нужны ли сертифицированные средства — принимает специалист по ИБ или юрист.

## 1. Как защищены данные

### Шифрование

| Где данные | Как защищены | Статус |
|---|---|---|
| **В пути** (браузер/приложение ↔ сервер) | TLS 1.2/1.3 через хостовый Nginx и Let's Encrypt, HSTS | ✅ с доменом. ⚠️ **В режиме «по IP» шифрования нет** — только для проверки |
| **Пароли** | argon2id — необратимый хэш, пароль не хранится и не может быть восстановлен даже администратором | ✅ |
| **Токены сессий, сброса пароля, привязки Telegram** | Хранится только SHA-256. Утечка базы не даёт войти в чужой аккаунт | ✅ |
| **Ссылки «управлять записью»** | HMAC-SHA256 от id записи, в базе только хэш | ✅ |
| **Бэкапы** | AES-256 (GPG), шифруются потоком — незашифрованный дамп на диск не попадает | ✅ |
| **База данных на диске** | Сама база не шифруется. Защита: изолированный том Docker, база недоступна из сети, права root на сервере | ⚠️ см. п. 3 |
| **Секреты** (пароли БД, ключи) | `.env` с правами 600 (только root), не попадают в git и в образы | ✅ |

**Что требует 152-ФЗ про шифрование.** Закон не требует шифровать всё подряд. Он требует принять меры по постановлению Правительства № 1119 и приказу ФСТЭК № 21 в соответствии с уровнем защищённости. Для сервиса записи (имя, телефон, история визитов — «иные» ПДн) обычно это 4-й уровень.

Сертифицированные средства криптозащиты (ГОСТ) нужны, только если модель угроз признаёт актуальными угрозы, которые нейтрализуются шифрованием. Для малого сервиса на старте обычно достаточно TLS и описанных мер. Это решение стоит зафиксировать в «Модели угроз» вместе со специалистом.

### Изоляция и доступ

- **Изоляция салонов на уровне базы (Row Level Security).** Даже ошибка в коде не покажет одному салону данные другого — это проверяют автотесты.
- **Три роли базы данных** (принцип наименьших привилегий):
  - `salon_app` — приложение, видит только свой салон;
  - `salon_owner` — миграции и системные задачи, не суперпользователь: не может читать файлы сервера и запускать программы;
  - `postgres` — только бэкапы.
- **Роли сотрудников:** владелец, управляющий, администратор, мастер. Мастер видит только свои записи, выгрузка клиентов доступна владельцу и управляющему.
- **Сеть:** база во внутренней сети Docker без выхода в интернет. Наружу открыт только Nginx.
- **Контейнеры:** лимиты памяти, запрет повышения привилегий, у приложения отобраны все системные привилегии (capabilities), процесс работает не от root.

### Защита от атак

| Угроза | Защита |
|---|---|
| Подбор пароля | Блокировка аккаунта после 5 ошибок на 15 минут; ограничение частоты запросов по IP |
| Кража сессии | Токен доступа живёт 15 минут; refresh-токен меняется при каждом использовании, а повторное использование старого отзывает все сессии; cookie `HttpOnly` + `SameSite=Lax` |
| CSRF | Для cookie-сессий изменяющие запросы требуют специальный заголовок; посторонние сайты в CORS не разрешены |
| XSS | React экранирует вывод; строгая CSP: скрипты только с нашего сервера |
| SQL-инъекции | Все запросы параметризованы (Prisma) |
| Встраивание во фрейм (clickjacking) | `X-Frame-Options`, `frame-ancestors 'self'` |
| Спам онлайн-записями | Не больше 3 будущих онлайн-записей на номер, платных SMS нет (нечего «накручивать»), ловушка для ботов (honeypot), ограничение частоты |
| Подделка вебхуков | Telegram — секретный заголовок; ЮKassa — проверка IP и повторный запрос статуса платежа у ЮKassa |
| Подделка IP через `X-Forwarded-For` | Заголовку доверяем только от своего прокси |
| Формулы в Excel-выгрузке (CSV-инъекция) | Опасные ячейки экранируются |
| Утечка секретов в логи | Токены в адресах маскируются; ротация логов |
| Уязвимые зависимости | `pnpm audit`: в серверной части уязвимостей нет; 2 средние — в инструментах сборки Expo, на сервер не попадают |

### Требования 152-ФЗ, реализованные в продукте

| Требование | Реализация |
|---|---|
| Локализация в РФ (ч. 5 ст. 18) | VPS и хранилище бэкапов — в России (выбор провайдера) |
| Отдельное согласие (ст. 9) | Отдельная галочка при регистрации и при онлайн-записи, тексты `/consent` и `/b/<салон>/consent` |
| Доказательство согласия | В журнале: версия текста, дата, IP, браузер |
| Политика обработки (ст. 18.1) | Опубликована: `/privacy` |
| Поручение обработки (ч. 3 ст. 6) | Раздел 5 оферты: салон — оператор, MioFlow — обработчик |
| Права субъекта: удаление | Удаление аккаунта в приложении; удаление клиента обезличивает его данные; данные удалённых салонов стираются через 30 дней |
| Выгрузка данных | Клиенты — в Excel |
| Журнал действий | `AuditLog`: изменения, выгрузки, согласия |
| Специальные категории ПДн не собираются | Подсказки «аллергии» убраны, в документах прямой запрет |
| Трансграничная передача | По умолчанию выключена. Telegram и push включаются отдельно, после уведомления РКН. Шрифты отдаются со своего сервера, без запросов к Google |

## 3. Нужны ли отдельные серверы для базы и бэкапов

**Для базы — пока нет.** На старте (до ~100 салонов) база в Docker на том же VPS — нормальная практика. Она изолирована: внутренняя сеть, лимит памяти, свой том. Отдельный сервер или управляемая база (Yandex Managed PostgreSQL, Selectel DBaaS) имеет смысл, когда появится нагрузка или понадобится резервирование. Стоит это от ~2 000 ₽/мес.

**Для бэкапов — да, обязательно отдельное место.** Но не VPS, а **объектное хранилище S3 в России**: Yandex Object Storage, Selectel, VK Cloud. Это дешевле (десятки рублей в месяц за гигабайты) и надёжнее. Бэкап на том же сервере не спасёт, если сервер сломается, его взломают или провайдер его потеряет.

Настройка (один раз):

1. Создайте бакет и сервисный ключ доступа в Yandex Object Storage.
2. Установите rclone: `sudo apt-get install -y rclone`.
3. Создайте подключение: `sudo rclone config` → `n` (new) → имя `yandex` → тип `s3` → провайдер `Other` → endpoint `storage.yandexcloud.net` → ключи.
4. В `.env` укажите `BACKUP_RCLONE_REMOTE=yandex:имя-бакета`.

Бэкапы шифруются **до** отправки, поэтому хранилище видит только зашифрованные файлы.

## 4. Проверки, которые выполняются автоматически

- **28 автотестов API**, в том числе:
  - изоляция салонов;
  - гонки при записи;
  - кража refresh-токена;
  - CSRF;
  - блокировка после неудачных входов;
  - восстановление пароля;
  - лимит онлайн-записей.
- **Дымовой тест в GitHub Actions** (`.github/workflows/docker.yml`) поднимает весь стек из готовых образов. Он проверяет:
  - заголовки безопасности;
  - роли базы данных;
  - что порт базы не открыт наружу;
  - бэкап и восстановление из него.

## Данные в телефоне (офлайн-режим)

Чтобы приложение работало при плохом интернете, расписание и карточки записей (имена и телефоны клиентов) хранятся на устройстве сотрудника до 7 дней. При выходе из аккаунта, удалении аккаунта или отзыве доступа (ответ 401) сохранённые данные и очередь отметок удаляются. Сотрудникам стоит включать блокировку экрана на телефоне — это стоит прописать в правилах салона для работы с ПДн.
